\subsection{Spark Profiler and Bounded Evidence}
The profiler (\texttt{services/spark/profiler.py}) is the only component that reads $D$. For each column it classifies a \emph{semantic type} (integer, float, string, date-like string, boolean) separately from the physical Spark dtype, computes null statistics, distinct counts, IQR outlier bounds, case/whitespace-normalised \emph{variant groups} for categorical columns, and a histogram of detected date patterns. Identifier-like columns (an \texttt{id} name pattern and $\geq90\%$ distinct values) are excluded from duplicate criteria. The profiler emits one evidence item per detected issue and none for issues it did not detect. Evidence carries raw values only where an issue was found, for example the variant histogram $\{\texttt{Engineering}{:}4,\texttt{engineering}{:}1,\texttt{ENGINEERING}{:}1\}$, and is capped at 30 distinct values and 10 sample rows. The prompt builder also removes per-column samples and top-value lists, so values from a column with no detected issue (such as employee names in S5) are never sent to the model. Besides enforcing P1, this keeps the prompt at $O(m+|E|)$ regardless of $n$, which E3 confirms empirically.

\subsection{Operation Catalog and Safety Tiers}
Table~\ref{tab:catalog} lists the eight operations. Each is implemented with the DataFrame API only; there is no \texttt{spark.sql()}, no \texttt{eval}, and no dispatch on parameter content. \textsc{Safe} operations rewrite values without inventing new ones. \textsc{Review} operations synthesise values or change the row count, and their verdict is capped at \textsc{needs\_review} however strong the evidence. \textsc{Finding} operations never execute. One registry generates the prompt's operation list, the validator's rules and the traceability map, so the three cannot disagree (ADR-002). As \S\ref{sec:res-audit} shows, the catalog's evidence requirements are themselves part of the safety argument: \texttt{NORMALIZE\_CASE} accepts whitespace evidence, and that single entry accounts for most of the damage the shipped validator lets through.

\subsection{AI Provider and Prompt Contract}
A provider implements one method, \texttt{generate\_\allowbreak{}recommendations(\allowbreak{}ProfileResult)} $\to$ \texttt{list[\allowbreak{}Recommendation]}, plus three identifying properties. The signature enforces P1 and P2: no parameter can carry raw data in and no return type can carry code out. There are two implementations, a remote Gemini provider~\cite{gemini2023} with native response-schema enforcement and a local Ollama provider with JSON-schema-constrained decoding~\cite{willard2023outlines} at temperature 0. Both use the same versioned system prompt, whose eight rules tell the model to treat Spark's numbers as given, not to compute or invent facts, to use only catalog operations, never to emit code, to cite evidence with checkable claimed values, and to return fewer recommendations when evidence is thin. Output is parsed strictly and a malformed item fails the stage with a typed error. The \texttt{operation} field is a free string rather than an enum, so that an invented operation still parses and is rejected by the validator with a recorded reason.

\subsection{Independent Validator}
The validator (Algorithm~\ref{alg:validator}) is built once per profile and imports nothing from the provider, executor or orchestrator (ADR-003). Rules run in a fixed order and stop at the first failure; every check is stored with a message. The evidence rules do the most work. They ignore the model's own \texttt{evidence\_refs} when deciding whether evidence exists and search $E$ directly for an item of a required type that covers the targets; for row-level operations the criteria set must equal the profiler's exactly. The model's claimed values are then compared with the matched evidence (numeric tolerance $10^{-6}$), and every raw key in a category mapping must appear in the variant histogram. One implementation detail turns out to matter: when several evidence items match, the claim check compares against the first one only (line 14). \S\ref{sec:res-audit} traces three false rejections to this choice.

\begin{algorithm}[t]
\caption{Evidence-based validation $V(r;P,E)$}
\label{alg:validator}
\footnotesize
\begin{algorithmic}[1]
\Require recommendation $r=(o,C_r,\theta,\cdot,\mathrm{refs})$; profile $P$; evidence $E$
\If{$o\in\mathcal{F}$ \textbf{or} $o\notin\mathcal{O}$} \Return \textsc{rejected} \Comment{R1, R8}\EndIf
\If{$C_r=\emptyset$ \textbf{or} $C_r\not\subseteq C$} \Return \textsc{rejected} \Comment{R2}\EndIf
\If{$\neg\mathrm{rowlevel}(o)\wedge\exists c\in C_r:\mathrm{sem}(c)\notin S(o)$} \Return \textsc{rejected}\EndIf
\If{$\theta$ has unknown keys, missing/ill-typed required keys, or values $\notin$ allowed} \Return \textsc{rejected}\EndIf
\If{$R(o)\neq\emptyset$}
  \State $M\gets\{e\in E:\tau_e\in R(o)\wedge(\mathrm{rowlevel}(o)\,?\,C_e{=}C_r : C_r{\subseteq}C_e)\}$
  \If{$M=\emptyset$} \Return \textsc{rejected} \Comment{R6: no Spark evidence}\EndIf
  \ForAll{$\mathrm{ref}\in\mathrm{refs}$}
    \State $e\gets$ first $e\in M$ with $\tau_e=\tau_{\mathrm{ref}}$, $C_{\mathrm{ref}}\subseteq C_e$
    \If{$\exists k: |\mathrm{ref.claimed}[k]-\sigma_e[k]|>\epsilon$} \Return \textsc{rejected}\EndIf
  \EndFor
  \If{$o=\texttt{STANDARDIZE\_CATEGORY}\wedge\mathrm{keys}(\theta.\mathrm{map})\not\subseteq\bigcup_{e\in M}\mathrm{variants}(e)$} \Return \textsc{rejected}\EndIf
\EndIf
\If{$t(o)=\textsc{finding}$} \Return \textsc{not\_executable}\EndIf
\State \Return $t(o)=\textsc{safe}\ ?\ \textsc{approved\_auto} : \textsc{needs\_review}$
\end{algorithmic}
\end{algorithm}

\subsection{Approval Boundary and Pipeline State Machine}
The orchestrator moves each run through ten states: \textsc{ingested} $\to$\allowbreak{} \textsc{profiled} $\to$\allowbreak{} \textsc{ai\_analyzed} $\to$\allowbreak{} \textsc{validated} $\to$\allowbreak{} \textsc{awaiting\_approval} $\to$\allowbreak{} \textsc{executing} $\to$\allowbreak{} \textsc{cleaned} $\to$\allowbreak{} \textsc{stats\_computed} $\to$\allowbreak{} \textsc{insights\_generated} $\to$\allowbreak{} \textsc{completed}, with \textsc{failed} reachable from any of them. Every transition is timestamped and persisted. The run stops at \textsc{awaiting\_approval} until each recommendation has an explicit decision. Interactively, a person approves \textsc{needs\_review} items; in experiments a written policy approves exactly what the validator marked executable. P4 is enforced in two places: \texttt{submit\_decision} raises an error if asked to approve an ineligible recommendation, and the experiment adapter combines any policy with the validator's verdict by logical AND, so a misconfigured policy rejects rather than crashes.

\subsection{Spark Executor}
Approved recommendations become a frozen \texttt{ExecutionPlan} ordered by a fixed precedence (type conversion, imputation, text and category normalisation, date formatting, deduplication), so that, for instance, trimming happens before duplicates are detected. The executor applies the plan in order, re-checks every parameter, and on the first failure skips the remaining operations and writes no output (P5).

\subsection{Comparison and Insights}
The cleaned table is profiled again with the same profiler and each issue is classified as resolved, improved, unchanged, worsened or introduced. Insights are produced from templates, not by the model; the system never asks the model to judge its own repairs (ADR-007, ADR-009).

\subsection{Design Rationale}
Three choices shaped the design. First, the model selects from a catalog instead of writing Spark or SQL code, which keeps the set of possible actions finite and testable. Second, the validator checks proposals against an artefact the model did not produce. Asking the model, or a second model, to check its own output risks correlated errors, while a check against Spark's evidence does not depend on the model at all. Third, the \textsc{Spark\_Only} baseline is deliberately narrow. It applies only the two repairs that the evidence determines completely and does not adopt heuristics such as ``the most frequent spelling is canonical''. A deterministic rule can still be wrong, and keeping the baseline narrow marks where semantic judgement becomes necessary.
